# RADIOROC2 — כלי צד מחשב

## התקנה

```bash
pip install pyserial openpyxl pillow
```

`pyserial` נדרש לחיבור ללוח. `openpyxl` נדרש לייצוא Excel — בלעדיו הייצוא נופל חזרה ל־CSV, והשאר עובד רגיל. `pillow` נדרש לצילומי מסך — בלעדיו כפתור הצילום אומר את זה ושאר האפליקציה לא מושפעת.

## הקבצים

| קובץ | תפקיד |
|------|-------|
| `rr2_gui.py` | האפליקציה הראשית — הפעל את זה |
| `rr2_decode.py` | פענוח פרוטוקול המסגרות. **חייב לשבת באותה תיקייה** |
| `rr2_thscan.py` | מנוע סריקת הסף, וגם כלי שורת פקודה בפני עצמו. **חייב לשבת באותה תיקייה** |

`rr2_gui.py` מייבא את המפענח מ־`rr2_decode.py` כדי שיהיה מקור אמת אחד לפרוטוקול. אם תשנה את המסגור בקושחה, יש לעדכן רק קובץ אחד. אותו היגיון חל על `rr2_thscan.py`: עמוד Scan מחליף רק את לולאת ההמתנה במכונת מצבים של Tk, ומה שנקודה אומרת, מה המסקנה, ומה נכתב לקובץ מגיעים כולם משם — כך שסריקה מהחלון וסריקה מהטרמינל הן אותה מדידה.

## החיבור ללוח

הלוח משדר דרך **USART3 → ה־VCP של ה־ST-Link**, כלומר כבל USB אחד נושא גם את הדיבאגר וגם את הנתונים. אין יותר מחבר USB נפרד.

זה UART אמיתי ולא CDC, ולכן **קצב השידור קריטי**: 921600, חייב להתאים ל־`RR2_LINK_BAUD` ב־[usart.h](../Core/Inc/usart.h). קצב לא נכון נותן ג׳יבריש, לא שקט.

שני הכלים מזהים את ה־ST-Link לבד לפי VID/PID, אז אין צורך לחפש את מספר ה־COM (שממילא משתנה בין שקעי USB).

```bash
python rr2_decode.py --list      # אילו פורטים יש, ומי מהם ה-ST-Link
```

## שעון ה־Slow Control של ה־ASIC

ה־ASIC דורש `clk_sm_i2c = 20 × SCL` בדיוק. השעון יוצא מ־**PA9 / TIM1_CH2** ב־2 MHz מול SCL של 100 kHz, ומוגדר ב־[tim.c](../Core/Src/tim.c) מתוך ה־`.ioc`.

> ⚠️ **אם מעלים את הקצב** — כלומר מגדילים את SCL, ואיתו את `clk_sm_i2c` מעבר ל־2 MHz — צריך להעביר את PA9 מ־`GPIO_SPEED_FREQ_LOW` ל־`GPIO_SPEED_FREQ_HIGH`. ב־`LOW` זמן הנפילה הוא עשרות ns וזה נגיס מכל חצי־מחזור; ב־2 MHz זה עדיין בסדר, מעל זה כבר לא.
>
> **משנים ב־CubeMX, לא ביד:** `System Core → GPIO` → PA9 → `Maximum output speed` → `High` → Generate. השורה ב־`tim.c` יושבת **מחוץ** ל־`USER CODE`, אז עריכה ידנית תימחק ב־generate הבא.
>
> שים לב שזה משפר רק את הקצה **היורד**. הקצה העולה נשלט ע"י ה־pull-up של 2.2k ב־PCA9306 ולא ע"י ה־STM32, ולכן לא מושפע מההגדרה הזאת.

## הפעלה

```bash
python rr2_gui.py            # רגיל
python rr2_gui.py --sim      # מצב סימולציה, בלי חומרה
python rr2_decode.py         # שורת פקודה, מזהה את הפורט לבד
python rr2_decode.py --csv out.csv
```

**מצב הסימולציה** מייצר פסגה גאוסיאנית סביב ADC 2400 עם זנב דמוי־קומפטון, בקצב ~180 cps. שימושי כדי ללמוד את הממשק ולבדוק את זרימת העבודה לפני שהלוח מולחם.

## מבנה הדפים

```
Main ─┬─ Settings   פרמטרי ASIC + קונסולת פקודות
      ├─ Measure    מדידה עם היסטוגרמה חיה
      ├─ Scan       סריקת סף: קצב לכל DAC1
      ├─ History    מדידות שמורות + ייצוא Excel
      └─ Help       הוראות
```

## סדר עבודה מומלץ

1. **Main** → בחר פורט → Connect (או Simulator)
2. **Settings** → הפעל את הערוץ הנכון → Apply global
3. **Scan** → Start scan → קבע את הסף שהיא ממליצה עליו, עם מרווח
4. **Measure** → מלא **Run label** → בחר ערוץ → Start
5. **History** → בחר מדידה → Export to Excel

הקושחה כבר מחילה באתחול את גיטור הערוצים ואת `Preset CsI` — אין צורך לעשות
אותם ידנית, וזה גם מה שמחזיר את המערכת לתצורה נכונה אחרי נפילת מתח. `stat`
מראה `hold_ns`, שאמור לצאת סביב 5900 בתצורת CsI ולא 3000.

## סריקת סף אוטומטית

הסריקה קיימת בשתי צורות שהן אותה מדידה: **עמוד Scan** בתוכנה, ו־`rr2_thscan.py`
משורת הפקודה. שתיהן מציבות כל ערך של DAC1 בתורו, מוודאות מול הלוח שהוא באמת
נכנס, שוהות, ורושמות את הקצב — ושתיהן כותבות אותו זוג `CSV` + `JSON` לתיקיית
`scans/`.

מהחלון: **Main → Scan → Start scan**. הטבלה מתמלאת שורה־שורה, ואפשר לעבור
לעמודים אחרים בזמן שהיא רצה. משורת הפקודה:

```bash
python rr2_thscan.py                                   # 320 עד 80, בצעדים של 20
python rr2_thscan.py --start 300 --stop 150 --step 10
python rr2_thscan.py --values 300,280,260 --label T30_HV27.14
```

**לא את שתיהן יחד**: לפורט טורי יש בעלים אחד, אז הכלי משורת הפקודה דורש
ש־`rr2_gui.py` יהיה סגור. גם בתוך התוכנה עצמה סריקה ומדידה לא רצות במקביל —
סריקה מזיזה את הסף כל כמה שניות, וספקטרום שנצבר על פני זה הוא סכום על הגדרות
שהרשומה תדע לנקוב רק באחת מהן. מי שינסה יקבל הודעה ולא ריצה מקולקלת.

הקצב לא נספר לפי מסגרות שהגיעו. מתחת לקיר הרעש ה־ASIC יורה הרבה מעבר למה
ש־921600 baud נושא, וכל מה שמעבר נזרק בתוך הקושחה — ספירת מה שהגיע הייתה
משטיחה את ראש העקומה בדיוק במקום שהסריקה קיימת כדי למצוא. הקצב נלקח ממוני
מסגרת הסטטוס: `trigger_count` נספר בפסיקה של NOR_T1OC, ולכן הוא סופר כל טריגר
שהשבב ייצר — גם את אלה שהקריאה שלהם דולגה, וגם את אלה שהמסגרת שלהם לא נכנסה
לקו. המכנה הוא `uptime_ms` של הלוח ולא שעון המחשב, כך שמסגרת סטטוס שנזרקה רק
מרחיבה את החלון ולא מעוותת אותו.

| עמודה | מה היא אומרת |
|-------|---------------|
| `trig_cps` | מה ש־NOR_T1 באמת עשה — זו הסריקה |
| `read_cps` | מה שהקושחה הספיקה לדגום — זמן מת, בערך 38 µs לאירוע |
| `host_cps` | מה ששרד את הקו — רוחב פס, בערך 3100 אירועים לשנייה |
| `excess` | חציון ערוץ האות מעל הפדסטל |
| `trig_counts` | הספירה הגולמית. השגיאה היחסית היא `1/sqrt(N)` |

`excess` הוא מה שמפריד מקור מרעש. הורדת הסף מכניסה גם עוד קומפטון וגם עוד
רעש, ושניהם נראים כמו מספר שעולה. הערוצים החשוכים 1–3 נמדדים באותם אירועים
ולכן החציון שלהם **הוא** הפדסטל — באותה טמפרטורה, בלי ריצה נפרדת — וטריגר
שלא מרים את ערוץ האות מעליו לא נשא אנרגיה. כשה־`excess` קורס לאפס, הקצב הפסיק
להיות פיזיקה. הכלי אומר את זה בסוף: איפה הקיר, ומהי הנקודה הנקייה בעלת הקצב
הגבוה ביותר.

נקודה נעצרת מוקדם ברגע שאספה `--counts` טריגרים, כך שסף שקט מקבל את מלוא
ה־`--dwell` ורועש נגמר בשנייה. ב־3 cps של רקע גם 30 שניות נותנות בערך 90
ספירות, שהן 11% — אם צריך יותר טוב בקצה השקט, הגדל את `--dwell`.

הסף מוחזר לאן שהיה כשהסריקה נגמרת. משורת הפקודה זה תקף גם ב־Ctrl-C, גם
בקריסה, וגם כשלוחצים Ctrl-C שוב בזמן ההחזרה עצמה; אם ההחזרה לא אושרה מול
הלוח, הכלי צועק וחוזר עם קוד יציאה 1. בתוכנה זה תקף ב־Stop, ב־Disconnect
ובסגירת החלון — בשני האחרונים הפורט עומד להיסגר ואין זמן לאשר, אז התוכנה
שואלת קודם ואומרת במפורש שההחזרה לא אושרה.

## מודדים קו אחד: OUT_AMUXLG

שתי היציאות מחווטות ל־ADC של ה־STM32 — OUT_AMUXLG ל־PA5 / ADC2_IN5 ו־OUT_AMUXHG ל־PA4 / ADC1_IN4 — אבל הקושחה קוראת רק את **OUT_AMUXLG**. לכן כל אירוע נושא ערך אחד לכל ערוץ, ציר ה־X בהיסטוגרמה הוא ספירות ADC גולמיות, ואין מה לבחור בין מסלולי הגבר ואין מה לכייל ביניהם.

אין מגבר בין ה־ASIC ל־ADC, ו־OUT_AMUXLG לא מוציא יותר מ־**1.32V**. מול VREF+ של 3.3V זו **תקרה של 1638 קודים** מתוך 4095 — כלומר 40% מטווח ה־ADC, והשאר לא ניתן להגעה. זה לא פוגע ברזולוציה (רעש הקוונטיזציה, 0.29 קודים RMS, קטן בסדרי גודל מרעש ה־SiPM וה־front־end), אבל זה קובע איפה נמצאת הרוויה: ההיסטוגרמה נפרסת על 0־1638, ומונה **saturated** סופר אירועים מ־1622 ומעלה.

מכאן ש־**lgGain** הוא הכפתור לגובה הפולס: אם הפוטו־פיק יושב בתא העליון ומונה ה־saturated מטפס, מוצא ה־LG נחתך על התקרה שלו — הורד lgGain, או הורד את מתח היתר של ה־SiPM דרך inDac. אם כל הספקטרום נדחס לתאים הראשונים — העלה lgGain. היעד הוא פוטו־פיק סביב **1100 קודים**, שני שלישים מהתקרה.

מסלול ה־HG עדיין קיים בשבב וטריגר המטען נגזר ממנו, אבל אף אחד לא קורא אותו: הפד OUT_AMUXHG אמנם מחווט ל־PA4 / ADC1_IN4, אך הקושחה לא מדגמת אותו והמאגר שלו נכתב כבוי. לכן אין לו שדות בעמוד Settings, ו־**Apply channel** משאיר את הרגיסטרים שלו בדיוק כפי שהיו.

אם בכל זאת צריך להגיע אליו, הקונסולה מקבלת ארגומנט שני אופציונלי:

```
ch 0 gain 4 6      lgGain=4, hgGain=6
ch 0 gain 4        lgGain=4, ה־HG לא משתנה
```

## ⚠️ למה Preset CsI חשוב

ברירת המחדל של ה־ASIC היא צעדי עיצוב של **20 ns**. זמן הדעיכה של CsI(Tl) הוא בערך **1 µs** — פי חמישים. בלי `slowShaping` המטען לא נאסף במלואו ורזולוציית האנרגיה נהרסת.

ה־preset מפעיל slow shaping בשני המסלולים, קובע peaking סביב 1.8 µs, ומותח את ה־hold delay בהתאם. זו **נקודת מוצא** — אחרי שיהיה מקור, סרוק את ה־Hold delay ותעקוב אחרי מיקום הפוטו־פיק.

## מחוון תקינות התקשורת

פורט פתוח לא אומר שהלוח מדבר: ה־ST-Link נרשם ב־Windows גם כשהקושחה לא רצה, ובקצב
שידור שגוי כל בית מגיע כזבל. לכן הקושחה שולחת מסגרת סטטוס **פעם בשנייה, תמיד** —
גם כשלא מודדים. המנורה ב־Main, ב־Measure ובשורת הסטטוס עוקבת אחרי הדופק הזה:

| מנורה | משמעות |
|-------|---------|
| ירוק — link ok | דופק הגיע בשתי השניות האחרונות, ושום דבר לא נכשל בעשר האחרונות |
| כתום — link unstable | הקישור חי אבל משהו לא בסדר, והטקסט אומר מה: דופק שנעדר, מסגרות שהלוח זרק, קריאה שנכשלה, שגיאות CRC, או ASIC שלא עונה ב־Slow Control. ייתכן שחסרות ספירות. מופיע גם בשניות הראשונות אחרי חיבור (`waiting for the first heartbeat`) — עוד לא יודעים זה לא פסק דין |
| אדום — no data | שלוש וחצי שניות בלי דופק. הלוח נותק, אותחל, או לא רץ. אם בתים כן מגיעים אבל שום דבר לא מפוענח — קצב שידור שגוי, והטקסט אומר זאת |
| אפור — offline | אין פורט פתוח |

פערי הדופק נמדדים לפי **שעון הלוח** (`uptime_ms` שבתוך המסגרת), לא לפי שעון המחשב,
כדי שממשק שנתקע לרגע בציור לא ידווח כקישור שדילג על פעימה.

**Test link** ב־Main בודק את הכיוון ההפוך: הדופק מוכיח שהלוח משדר, וזה מוכיח שהוא
גם מקשיב. קישור שבו מסגרות מגיעות אבל פקודות הולכות לאיבוד נראה תקין לגמרי — עד
שהגדרה נכשלת בשקט.

בזמן מדידה השורה מתחת לגרף אומרת איזה סוג של שקט זה: `LINK DOWN` פירושו שהשניות
שעוברות לא נרשמות בכלל, ואילו `link ok, no events` פירושו שהלוח בסדר ופשוט שום דבר
לא מפעיל טריגר — סף, ערוץ מושבת, או שאין מקור.

התחלת ריצה כשהמנורה אדומה או כתומה מבקשת אישור, ומה שהמנורה אמרה נשמר עם המדידה
בכל מקרה.

## מה נשמר עם מדידה

`Save measurement` שומר את ההיסטוגרמה ואיתה את מצב המערכת ברגע שהריצה התחילה:

- **הרגיסטרים של ה־ASIC, כפי שנקראו מהלוח.** בתחילת ריצה נשלחים `stat` ו־`ch N dump`,
  והתשובה מפוענחת לערכים בעלי שם: inDac, lgGain, tauLG, הספים, השהיית ה־hold, והאם
  מסלול ה־LG מוזן. זה מה שהשבב היה מוגדר אליו בפועל, לא מה שהטופס אמר.
- **עמוד Settings כפי שהיה**, בנפרד. איפה שהשניים לא מסכימים, History מציג
  `Form and chip disagree` — כך ערך שהוקלד ולא הוחל מסגיר את עצמו, חודשים אחרי.
- **הגדרות הרכישה**: ערוץ, תאים, טווח, המשך שהתבקש, והאם רישום raw היה פעיל.
- **תנאי הריצה שהוקלדו** — החצי שהלוח לא יכול לדעת. ראה למטה.
- **סימני החיים של הקישור**: הפסק בהתחלה ובשמירה, כמה מסגרות סטטוס ואירועים הגיעו,
  פער הדופק הגרוע ביותר, כשלי CRC, והמונים של הלוח עצמו (טריגרים, קריאות, זריקות).

הכול נמצא ב־JSON תחת `measurements/`, בחלונית שליד הגרף ב־History, ובגיליון
**Metadata** של ייצוא Excel — שורה לכל הגדרה.

ריצות שנשמרו בגרסה קודמת פשוט מציגות פחות מקטעים. במצב סימולציה אין רגיסטרים
לקרוא, ולכן נשמרים רק ערכי הטופס והרשומה אומרת למה.

## תנאי ריצה — Run conditions

הלוח יודע את הרגיסטרים של ה־ASIC ואת הטמפרטורה שלו עצמו. הוא לא יודע למה הוגדר ספק
ה־HV, מה עמד מול הגביש, או מה נאמר לתא. ששת השדות בעמוד **Measure**, מתחת ל־Setup,
הם החצי הזה — ובלעדיו סריקה תרמית לא ניתנת לניתוח בדיעבד:

| שדה | מה כותבים בו |
|------|---------------|
| `Isotope` | `Cs-137` / `Co-60` / `no source`. **ריק זו ברירת המחדל** — `no source` היא מדידת רקע אמיתית, וריצה שלא אמרה מול מה עמדה אינה הריצה ההיא |
| `Oven setpoint (C)` | מה שנאמר לתא. `temp_c` לידו ב־History הוא מה שהלוח הרגיש, וההפרש ביניהם הוא הגרדיאנט |
| `HV supply set (V)` | ה־setpoint בספק |
| `HV measured (V)` | מה שנמדד ביציאת הספק |
| `V at channel pins (V)` | נמדד על השקע **כשהחיישן מנותק** — זה HV פחות מה שה־inDac מחזיק על הכניסה, כלומר מתח היתר שה־SiPM באמת יראה |
| `Note` | כל השאר: מרחק המקור, זמן ההשריה, איזו יחידת גלאי, מה השתנה באמצע |

מספר שנכתב כמספר נשמר כמספר, כדי ש־Excel יוכל לשרטט סריקה מולו. מה שלא מתפרש
נשמר כפי שהוקלד ולא נזרק. **השדות בכוונה לא נזכרים בין הרצות** — HV ישן שנדבק
בשקט לריצה של מחר גרוע יותר משדה ריק.

## מה כל ערך עושה

עמוד **Help** בתוכנה מסביר כל פרמטר: מה הוא, מה קורה כשמעלים אותו, מה קורה כשמורידים,
ומה זה עושה למדידה בפועל — לפי ערוץ, גלובלי, ועמוד Measure. יש שם אינדקס מקטעים
לקפיצה מהירה.

העמוד קיים באנגלית ובעברית. הבורר **language** בפינה העליונה מחליף ביניהן,
והבחירה נשמרת להרצות הבאות בקובץ `gui_prefs.json`. בגרסה העברית העמוד כולו
מתהפך לימין-לשמאל, והמונחים המקצועיים נשארים באנגלית — בדיוק כפי שהם
מופיעים בעמוד Settings ובקונסולת הקושחה.

## צילומי מסך

**F12**, או הכפתור בשורת הסטטוס למטה, שומר PNG של כל החלון לתיקיית `screenshots/`.
אין דיאלוג: הקובץ נשמר ושמו מופיע בשורת הסטטוס, כך שאפשר לצלם באמצע ריצה בלי
לעצור אותה.

**Save plot PNG**, ב־Measure וב־History, שומר את הספקטרום לבדו. ב־Measure הוא לוקח
גם את שורת המספרים שמתחת לגרף — הספירות, הקצב והטמפרטורה — וזה מה שהופך את התמונה
למשהו שאפשר לשים ביומן מעבדה בלי לכתוב לידו כותרת.

`Run label` נכנס לשם הקובץ בדיוק כמו ב־CSV הגולמי:

```
screenshots/spectrum_20260824_113000_T30_HV27.14.png
```

זה צילום של המסך עצמו, ולכן החלון מורם לחזית לרגע לפני התריס — אחרת חלון אחר
שמונח מעליו הוא מה שנכנס לתמונה. הצילום נשמר ברזולוציה הפיזית של המסך: בקנה מידה
200%, חלון של 1060×740 יוצא 2120×1480.

## אחסון

מדידות נשמרות כ־JSON בתיקיית `measurements/` ליד הסקריפט — ההיסטוגרמה, יחד עם
התנאים שבהם נמדדה.

עם `log raw events` מסומן (ברירת מחדל), כל אירוע נכתב גם ל־CSV בתיקיית `raw/`:
שורה לכל ערוץ, עם הטמפרטורה שהלוח דיווח עבור אותו אירוע.

```
seq,t_ms,temp_c,ch,lg
1,10,29.870,0,2401     ← ערוץ האות
1,10,29.870,1,123      ← ערוץ חשוך: קו הבסיס
1,10,29.870,2,127
1,10,29.870,3,121
```

ההיסטוגרמה היא ערוץ אחד; קובץ ה־raw הוא כל חלון הקריאה. **הערוצים החשוכים הם
הפדסטל** — נמדד בכל אירוע, בכל טמפרטורה, בלי ריצה נפרדת. הטריגר הגיע מערוץ
האות ולכן הוא בלתי תלוי ברעש שלהם, כך שאין הטיית בחירה כמו בפדסטל שנאסף
בהורדת הסף לתוך הרעש. כל ניתוח שצריך פדסטל צריך את הקובץ הזה.

**Run label** נכנס לשם הקובץ ולעמודה ב־History. מלא שם את נקודת הטמפרטורה ואת
ה־HV (`T30_HV27.14`) — זה מה שיבדיל בין שש הריצות אחר כך. שאר התנאים כבר לא צריכים
להידחס לשם הקובץ: יש להם שדות משלהם, ראה **תנאי ריצה** למעלה.
